Claude's research (his Notion page "Simple video editor: how hard to build (Nov 2026)"): doable in Chrome on the phone, harder than Idea board, with nearly all the difficulty in saving the finished video.

### November 2, 2026: everything on the phone; Mediabunny makes the video (pull request 110)
- Decision: the app makes the new video frame by frame in Chrome, with the browser's video tools (WebCodecs, Chrome 94 and later, Android included) and the free Mediabunny library (MPL-2.0; version 1.65.0, October 30, 2026). The videos never leave the phone.
- Why: Claude's research, November 2, 2026: Mediabunny's conversion tools have trimming, cropping, resizing and frame-by-frame drawing (for filters and text) built in, with progress and a way to stop, and it comes as one ready-made file (its README and guide on GitHub, and the npm registry).
- Turned down: ffmpeg.wasm (FFmpeg in the browser): its main file is 32.2 MB, and its own speed test took 60 to 129 seconds to convert a 10-second 720p clip on a computer (Intel Core i5, Chrome 116), so a phone would likely be slower (its FAQ and Performance pages on GitHub). "Play and record" with the browser's MediaRecorder: no library, but saving takes as long as the video plays, with the screen on, and whether Chrome on Android records MP4 couldn't be confirmed (a third-party table, addpipe's, says Chrome 126 and later can, without saying whether Android is included); kept as a backup plan. A server: the videos would leave the phone.
- Status: one planned exception, November 3, 2026: the plan for AI captions (pull request 140): for his captions only, the sound of the trimmed clip goes to his own Cloudflare server when he taps.

### November 2, 2026: Mediabunny's file saved in the folder, no npm (pull request 110)
- Decision: Mediabunny's ready-made file goes in `video-editor/lib/`, with its license and a link to its source, and the app loads it with `import`. One version stays until an update is chosen on purpose.

- Turned down: npm with a build step (a smaller download, by keeping only the parts of Mediabunny the app uses, but a build on every publish); loading Mediabunny from a CDN.

### November 2, 2026: the phone test page, and how Mediabunny loads (pull request 111)
- Decision: build step 2 is its own page, `video-editor/phone-test.html`, with `phone-test.js` and `phone-test.css`, kept after the app is built, for checking another phone or a Chrome update. Mediabunny loads with plain `<script>` tags: `lib/mediabunny.min.js` (its `mediabunny.min.cjs` build, renamed so the website sends it as JavaScript) sets a global `Mediabunny`. Mediabunny's AAC add-on (`lib/mediabunny-aac-encoder.min.js`) loads only when Chrome can't make AAC sound itself. The page has a safety rule (Content-Security-Policy) like Idea board's, plus `'wasm-unsafe-eval'` and `worker-src blob:` for the add-on.
- Why (Claude's choices, November 2, 2026): the add-on's module build imports "mediabunny" by name, which needs an import map, an inline script the safety rule would block; its plain build reads the global `Mediabunny` instead (seen in both files). Claude's test browser (Chromium 153) can make H.264 video but not AAC sound, so the add-on is a real need on some browsers; Mediabunny's docs: "In some browsers, AAC encoding is not supported by WebCodecs." Both downloads matched the npm registry's integrity hashes; their SHA-256 hashes are in `lib/README.md`, and the saved checks test them.
- Licenses: Mediabunny and the add-on are MPL-2.0 (`lib/LICENSE`, with links to their source). The add-on contains FFmpeg's AAC encoder, unmodified, under the LGPL 2.1 or later; its license files are in `lib/licenses/ffmpeg/`, with a link to FFmpeg's source and the build steps in `lib/README.md`.
- Turned down: modules with an import map (blocked by the safety rule without extra work); loading from a CDN (not reachable from Claude's session to test); making Opus sound instead of AAC when Chrome lacks AAC (whether other apps play Opus inside MP4 wasn't checked).

### November 2, 2026: what a copy keeps and doesn't (pull request 111)
- Decision: each copy is made with `tags: {}` (none of the original's tags), with the picture turned upright in the frames (`allowTransformationMetadata: false`), and at most 1920 pixels on its longest side (Reels are 1080 by 1920). The file's name isn't shown on the page.
- Why: Mediabunny's type notes for `Conversion` say: "If no function is set, the input's metadata tags will be copied to the output (excluding `creationTime`)." So the privacy plan in `SPEC.md` ("it shouldn't carry the original's hidden details") needed `tags: {}`. The saved checks confirm it: a test video with a location ("loci") makes a copy without one. Turning the picture upright in the frames means every player shows it the right way up; the check compares the copy's first frame with ffmpeg's upright view of the original. File names can be personal, and the owner sends screenshots.
- Also checked: the page looks for a location in the file's "moov" box only ("©xyz", "loci" or Apple's "quicktime.location"), so picture data can't cause a false alarm. Which of these Android phones write wasn't checked; the test shows what the owner's phone does.

### November 2, 2026: made for Instagram, TikTok and YouTube Shorts (pull request 112)
- Decision: every new video is made to fit the three platforms' upload rules: MP4 with its details at the front; H.264; at most 1920 pixels on the longest side; a steady 24 to 60 frames a second (the original's, rounded); 8 Mbps for 1080 by 1920 at 30 frames a second (10 at 60, less for smaller videos); AAC sound at 48 kHz, stereo, 128 kbps; no tags. "Your video" reads the new file back and checks it against the rules, with one line for each, and a line for Claude with the codec, color tags and edit lists.
- Why: Dan: "Also make sure the videos that are created can be used for Instagram, TikTok, and Youtube Shorts." The rules and their sources are in `SPEC.md` ("Made for Instagram, TikTok and YouTube Shorts"); every official page was seen only in search results, since developers.facebook.com, developers.tiktok.com, help.instagram.com and support.google.com are blocked from Claude's session. The strictest numbers come from Meta's rules for videos posted through its tools (300 MB, 25 Mbps, AAC at 48 kHz, 128 kbps): meeting those meets the looser ones. The data rates keep a 3-minute video under 300 MB (Claude's arithmetic: 8.1 Mbps for 180 seconds is about 183 MB).
- Known differences, left on purpose until real uploads say otherwise: one edit list on the sound track (it skips the AAC encoder's first 1,024 samples; Mediabunny has no setting to leave it out, and ffmpeg's MP4 files have the same kind by default), and full-range color tags in Claude's test browser (the phone's own may differ; the line for Claude shows them). Meta's and YouTube's strictest settings ask for no edit lists.
- Turned down: hacking the edit list out of the finished file (renaming its box), since it shifts the sound by 21 thousandths of a second and real uploads may show it's not needed; converting every frame to limited-range color by hand, which would slow every video down, before knowing what the phone makes.

### November 2, 2026: each new video made frame by frame (pull request 125)
- Decision (Claude's, told to Dan when step 4 started): the app makes the new video itself, frame by frame, instead of with Mediabunny's one-step `Conversion`. Frame number k of the new video shows the moment start + (k ÷ frame rate) × speed of the original (`CanvasSink`), drawn on a normal canvas with the look and added as H.264 (`CanvasSource`). The sound is gathered (`AudioBufferSink`), played at the speed in an `OfflineAudioContext` (48 kHz stereo) and made AAC (`AudioBufferSource`).
- Why: `Conversion` can trim but has no speed setting (its type notes, Mediabunny 1.65.0). Frame by frame handles trim and speed exactly, keeps a steady frame rate, and is the path better sound (step 5) and several clips (step 8) need. The file is written fresh, so none of the original's tags come along (`tags: {}` was a `Conversion` setting; the phone test still uses it).
- Checked in Claude's test browser, with a made-up "clock" video (a gray that brightens each second, and a 330 Hz tone): trimmed to 2 to 6 seconds at 2×, the new video is 2.0 seconds, a steady 30 frames a second, each frame shows the right moment, and the tone is 660 Hz; 0 to 2 at 0.5× is 4 seconds at 165 Hz; the whole 8 seconds at 1.5× is 5.3 seconds. The earlier checks (looks, lighting, the upload rules, Stop, Back) pass on the new path.
- Not checked yet: how long it takes on Dan's phone.

### November 3, 2026: better sound, three switches and a volume (pull request 129)
- Decision: a fifth tab, "Sound," with three switches, all off at first: "Cut rumble" (wind, traffic and bumps from holding the phone), "Clearer voice" (brings voices forward and takes out boominess) and "Even out the volume" (quiet words louder, loud moments softer), and a Volume slider from Off (0%) to 200% in steps of 10, with "Reset the sound." The playing video sounds the same way as the new video will.
- Why: Dan chose "B": "Three separate switches (Cut rumble, Clearer voice, Even out the volume), plus the Volume slider. You get more control, but there's more to think about." (Claude's words for the option.)
- Turned down: "A) One switch, 'Clearer sound,'" that turns on the first three fixes together, plus a Volume slider (Claude's recommendation: one tap, nothing to adjust); "C) Just the Volume slider for now." Also left for later (Claude's suggestion, told to Dan with the question): turning down a steady hiss like a fan or an air conditioner (without AI it helps only some, it's the most work, and pushed too far it makes voices sound watery). Other people talking or music in the background can't be removed without AI (the owner's no-AI rule).
- How (Claude's choices, measured with test tones in Claude's test browser, November 3, 2026): Cut rumble is two high-pass filters at 80 Hz (50 Hz 17.7 dB quieter, a voice's range almost unchanged); Clearer voice is 3 dB less around 300 Hz and 4 dB more around 3,500 Hz; Even out the volume is a compressor (above −30 dB, 4 to 1; a 30 dB gap became 18 dB); then the volume; then a safety limit (above −3 dB, 20 to 1), only when something is changed, so a louder volume never clips. The playing video's sound goes through the same steps from the first change on the Sound tab, so nothing changes for a video whose sound isn't touched. Each compressor holds the sound back 6 thousandths of a second; the new video's sound is moved back in line, and the saved checks show it lines up with the original to the sample (a hiss lined up both ways; a check that times a sudden tone was dropped, since AAC smears a sudden start by about 14 thousandths of a second with or without the steps).
- Not checked yet: how it sounds on Dan's phone with a real voice, and whether the playing video's sound stays in step with the picture there once it goes through Chrome's sound tools (they may add a small delay on a phone; unverified).

### November 4, 2026: how the captions server and the passcode are built (build step 7a)
- Decision (Claude's choices, for Dan to change if he likes):
  - One address, `POST /captions?language=en` (or `ko`): the passcode in the Authorization header, the sound as base64 text in the body, up to 700,000 letters (about 16 seconds of the app's sound), so build step 7b sends pieces of up to 15 seconds instead of the plan's 30. It sends back each word with its start and end, and the piece's length. The sound goes to the AI as it came, never decoded on the server.
  - The passcode is compared scrambled (SHA-256), byte by byte; capital letters and extra spaces don't matter (a phone's keyboard may add a capital). No lockout for wrong tries: it would need a database, and a passcode of four or more random words can't be guessed.
  - It keeps nothing: logs off (`observability` off in `wrangler.jsonc`; new Workers keep logs unless told not to), never `console.log`, no database. Version addresses off (`preview_urls: false`), so it has one address. Opening that address in a browser says whether it's running and set up (never the passcode). The same compatibility date as Living in the Word's server (2026-10-26), one Cloudflare already accepts on this account.
  - On the phone: "Captions, just for you" on the start screen, only with `?owner` in the address. The passcode box hides what's typed, like Living in the Word's. "Save and check" sends the passcode and one second of silence through the AI, so one check shows the passcode, the server and the AI all work, without anything of a video. The passcode is kept only when the server takes it (also when the AI is busy, failing or out of today's free captions). "Check it again" and "Forget the passcode." It's kept in the phone's `localStorage`, which every app at danielyoonwrites.github.io shares (like Living in the Word's passcode): they're all Dan's own code, and each page's safety rule blocks outside scripts. The page may talk to this one server only (its safety rule's `connect-src`), and never does without `?owner`.
  - In Dan's setup: preview builds off and build watch paths at `*`, like Living in the Word's.
- Why: on Cloudflare's free plan each request gets 10 thousandths of a second of the server's own work ("10 ms" of CPU time: Cloudflare's Workers limits, read November 4, 2026). Measured on Claude's computer (November 4, 2026, 60 tries each): a million letters (about 23 seconds) took about 5 thousandths in the middle and 700,000 (about 16 seconds) about 3.6, each with now and then a jump of 10 or more while memory is tidied up; decoding the sound or reading it as JSON would add more. Base64 is the way Cloudflare's own tutorial sends sound to this model; the other way in the model's file (a body with a content type) isn't described anywhere else in their docs.
- Turned down: the sound inside JSON (more of the server's time); sending the sound as a stream (undocumented); 30-second pieces (too close to the free plan's limit); a separate "check the passcode" address that skips the AI (the AI would stay unchecked until 7b).
