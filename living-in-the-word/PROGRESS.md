## How to run and check it
- Run: the app is plain files that GitHub Pages publishes after each merge. The server is the Cloudflare Worker `living-in-the-word`, which Cloudflare deploys after each merge, using `server/wrangler.jsonc`. Its secrets are kept in Cloudflare by name: `ANTHROPIC_API_KEY`, `PASSCODE`, `RESEND_API_KEY` and `OWNER_EMAIL` (`ESV_API_KEY` isn't set; the ESV is on hold). On Claude's computer: `python3 -m http.server 8765 --bind 127.0.0.1` from the repository folder, then http://127.0.0.1:8765/living-in-the-word/ (the server answers only the real site and this address).
- Check: from the repository folder, `node living-in-the-word/tests/server-test.mjs && node living-in-the-word/tests/app-test.mjs`. Success (since pull request 134): "116 passed, 0 failed", then "160 passed, 0 failed" (about a minute). The app checks use ports 8765 (the app) and 8766 (a stand-in site for the offline helper's checks), which must be free, and Playwright's Chromium (installed in Claude's cloud sessions). When `app.js` or `style.css` changes, raise its `?v=` in `index.html` and put the new fingerprint the VERSIONS check prints into `KNOWN` in `tests/app-test.mjs`.
- Stand-ins for new checks: in `tests/server-test.mjs`, `ai.fail = { status, body, headers }` makes the stand-in AI answer with that problem (section 24) and `ai.delay` slows it; `env.DB.hold()` holds every database batch until the function it returns is called, and `env.DB.waiting()` counts the held ones, so requests sent at the same moment all read before any adds (section 25); `env.DB.trips()` counts the trips to the database (section 26); in `tests/app-test.mjs`, `holdAnswer(passage)` holds one answer back until `release()`, `held` (a Map of passage to promise) holds several, `hang` never answers one passage, and `page.addInitScript` can shorten the app's 2-minute timer for one check (section HANG) or make every save fail, with `window.realSetItem` to put a sign-in there first (section NOSAVE). `context.route` also catches the offline helper's own requests (Playwright 1.63), which section SW4 uses for a slow stand-in Google Fonts. To prove a check catches a problem, run it on a scratch copy of `living-in-the-word/` with the old `app.js` (`git show HEAD:living-in-the-word/app.js`).
- Check the settings file without deploying: copy `server/worker.js` and `server/wrangler.jsonc` to a scratch folder and run `npx --yes wrangler@latest deploy --dry-run --outdir out` there. It should list `env.DB (living-in-the-word-limits)`.
- Try the server in Cloudflare's own local runtime (first used November 3, 2026; nothing is deployed): in a scratch folder with `server/worker.js`, `server/wrangler.jsonc` and a `.dev.vars` file of made-up secrets (`PASSCODE=...`, `OWNER_EMAIL=owner@example.com`), run `npx --yes wrangler@latest dev --local --port 8787 --ip 127.0.0.1` (a local database); add rows with `npx --yes wrangler@latest d1 execute living-in-the-word-limits --local --command "..."`, and send requests with the header `Origin: https://danielyoonwrites.github.io`. Its log warns it can't fetch `Request.cf`: harmless. Stop it afterwards (`pkill -f workerd`).
- Check a deploy: Cloudflare's "Workers Builds: living-in-the-word" check next to the merge, through https://api.github.com/repos/danielyoonwrites/danielyoonwrites.github.io/commits/<commit>/check-runs?filter=all. It can take up to about 10 minutes to appear (November 3, 2026). Its log is only in Dan's Cloudflare account. If a build fails, paste by hand meanwhile (https://dash.cloudflare.com, Compute, Workers & Pages, `living-in-the-word`, Edit code). If a deploy breaks the server, revert the pull request on GitHub (its "Revert" button) and merge the revert.
